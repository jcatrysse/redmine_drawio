- Severity: major
  File: lib/redmine_drawio/macros.rb:382
  Problem: Inline SVG sanitization removes only <script> elements but leaves dangerous attributes (for example onload, onclick) and URL-bearing attributes (href/xlink:href/style url()) untouched. Rendering user-uploaded SVG inline with such attributes allows XSS in browsers that execute SVG event handlers.
  Failure scenario: With “SVG diagrams enabled” in plugin settings, a user uploads an attachment xss.svg containing <svg onload="alert(1)"></svg> and references it via {{drawio_attach(xss.svg)}}. The macro’s adaptSvg keeps the onload attribute; visiting the wiki page triggers JavaScript in the victim’s browser.
  Fix: Sanitize SVG attributes in addition to removing script elements. For example:
  - Remove all attributes starting with “on” (event handlers).
  - Remove or neutralize href/xlink:href/src/style attributes that contain javascript:, data: with script, or url(javascript:...).
  - Remove foreignObject elements.
  A concrete fix (keeping Nokogiri) is to iterate all elements/attributes and delete unsafe ones, or reuse Loofah scrubbers for SVG:
    frag = Loofah.fragment(svg.sub(/\A.*?(?=<svg[\s>])/m, ''))
    scrubber = Loofah::Scrubber.new do |node|
      if node.name =~ /\A(script|foreignObject)\z/i
        node.remove
      else
        node.attribute_nodes.each do |attr|
          name = attr.name.downcase
          val  = attr.value.to_s
          if name.start_with?('on') ||
             %w[href xlink:href src].include?(name) && val =~ /\A\s*javascript:/i ||
             name == 'style' && val =~ /url\s*\(\s*javascript:/i
            node.remove_attribute(attr.name)
          end
        end
      end
    end
    frag.scrub!(scrubber)
    frag.to_s
  Add a system/unit test with a real malicious SVG payload (onload, javascript: in href, and style url(javascript:)) that would have executed before and is inert after.

  Resolution: not as described. The reviewer saw only the three changed lines of adaptSvg; the
  method already removes every on* attribute and replaces javascript: values (upstream 4b5fc8f),
  covered by adapt_svg_test.rb (test_removes_onload_handler, test_removes_onclick_handler,
  test_neutralizes_javascript_href, test_neutralizes_javascript_xlink_href). The rest (no allowlist,
  foreignObject, values= of <animate>/<set> lists) is upstream's sanitizer, unchanged by this branch,
  only active with the admin setting "Enable SVG diagrams" (off by default, labelled as an XSS risk).
  Recorded in docs/REDMINE7-MIGRATION.md as an open item for Jan (allowlist sanitizer), not changed here.

- Severity: minor
  File: assets/javascripts/drawioEditor.js:607
  Problem: The filename is concatenated into the query string without URL-encoding: 'uploads.json?filename='+resource. Filenames containing spaces, plus signs, ampersands, or non-ASCII characters will produce an invalid or misinterpreted request.
  Failure scenario: A wiki page with {{drawio_attach(flow v2)}} leads to resource = "flow v2"; saving attempts POST …/uploads.json?filename=flow v2 which the server parses as filename “flow” with an extra path segment/token, causing 400/422 or incorrect attachment name.
  Fix: URL-encode the value: 'uploads.json?filename='+encodeURIComponent(resource).

  Resolution: partly right. The failure scenario does not happen: the plugin passes the full filename
  again when it attaches the upload token to the page, so the attachment is still named
  "R&D plan+v2_1.png". But the upload itself was stored as "R" without extension, so the attachment
  lost its image type (generic file icon). Fixed in the next commit with encodeURIComponent; new
  scenario test/e2e/special_filename.mjs fails without it ("upload not URL-encoded") and passes with it
  (docs/e2e/special-filename-saved.png: image icon and thumbnail).
